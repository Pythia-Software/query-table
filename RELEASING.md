# Releasing

This project publishes four public npm packages from one versioned monorepo:

- `@pythia-software/query-table-core`
- `@pythia-software/query-table-react`
- `@pythia-software/query-table-ui`
- `@pythia-software/query-table-codegen`

All public packages, the private demo workspace, and the repository root must
carry the same version. Internal workspace dependencies must use that exact
version. `npm run version:check` enforces these invariants.

## One-time npm bootstrap

Trusted publishing is configured on an existing npm package, so the initial
`0.1.0` packages must first be created by an organization owner.

1. Merge the release-ready tree to `main`, make the GitHub repository public,
   and confirm CI passes on the exact commit to publish.
2. From a clean checkout of that commit, authenticate an npm organization owner
   with 2FA and run:

   ```bash
   npm ci --ignore-scripts
   npm run release:check
   npm publish --workspace @pythia-software/query-table-core --access public
   npm publish --workspace @pythia-software/query-table-react --access public
   npm publish --workspace @pythia-software/query-table-ui --access public
   npm publish --workspace @pythia-software/query-table-codegen --access public
   ```

3. In each package's npm settings, configure a GitHub Actions trusted publisher:

   - organization: `Pythia-Software`
   - repository: `query-table`
   - workflow filename: `release.yml`
   - allowed action: `npm publish`

4. For each package, set publishing access to require 2FA and disallow
   traditional tokens.
5. Create `v0.1.0` on the published commit and push the tag. The release workflow
   validates the tag and packages, recognizes that `0.1.0` already exists, and
   exits successfully without republishing it.
6. Create the matching GitHub release and verify all four registry packages from
   a clean consumer project.

The bootstrap release is interactive and does not receive the automatic
provenance generated by OIDC. Later releases do.

## Subsequent releases

1. Update the root, public workspace, private demo, and internal dependency
   versions together.
2. Move the relevant changelog entries from `Unreleased` into the new dated
   version.
3. Merge to `main` and wait for CI to pass.
4. From a clean checkout, run `npm ci --ignore-scripts` and
   `npm run release:check`.
5. Create and push an annotated `v<version>` tag on that exact `main` commit.
6. Wait for `.github/workflows/release.yml` to publish in dependency order using
   npm trusted publishing. The workflow rejects version mismatches and tags not
   reachable from `main`; reruns safely skip package versions already published.
7. Create the GitHub release and verify installation from the registry.

Never publish from a dirty worktree, move an existing release tag, or add a
long-lived npm write token to GitHub Actions.
